# 시간표 이력 설계 및 마이그레이션

## 목표

한 부원의 기존 `User` 행은 **현재 상태**로 유지하고, `RosterHistory` 시트에 실제 변경만 추가한다. 모든 날짜의 전체 시간표를 매일 복제하지 않는다.

| 열 | 의미 |
| --- | --- |
| id | 단조 증가하는 이벤트 ID (시트 행 기반) |
| userId | 변하지 않는 부원 식별자 |
| effectiveAt | 변경이 실제 반영된 UTC 시각 (ISO 8601) |
| patch | 변경된 필드만 있는 JSON |
| createdAt | 이벤트가 기록된 UTC 시각 |

지원하는 변경 필드는 `name`, `grade`, `day`, `shift`, `type`이다. 처음 한 번만 각 부원의 전체 값을 기록하며, 이후에는 변경된 필드만 기록한다.

예를 들어 `{"day":2}`, `{"shift":3}`, `{"grade":3,"type":1}` 같은 이벤트가 추가된다. 삭제는 `type:-1` 상태 변경으로 표현하며, 출석 기록을 가진 부원은 여전히 삭제할 수 없다.

현재 `User`는 조회 속도가 빠른 **물질화된 최신 상태**, `RosterHistory`는 변경 이력이다. 관리자 화면은 과거 날짜의 각 당번 마감 시각(점심 전 13:00, 점심 후 13:20, 저녁 18:20) 직전까지의 이벤트를 재생해 당시 시간표를 복원한다. CSV도 출석 날짜·시간대에 맞는 과거 학년과 배정 정보를 조회한다.

저장 공간은 학기 전체를 매일 복제하는 `O(학생 수 × 날짜 수)` 대신 `O(학생 수 + 변경 이벤트 수)`다. 부원 한 명의 필드 한 개만 바꾸면 이벤트 한 행에 그 필드 하나를 기록한다.

## 이전 데이터의 한계

**마이그레이션 이전에 일어난 시간표 변경을 복원할 수는 없다.** `setup_` 실행 순간의 `User` 상태를 기준선으로 저장하고, 스크립트 속성 `ROSTER_BASELINE_AT`에 UTC 시각을 남긴다. 이전 기록은 화면에서 이력 미확인으로 안내하며, CSV 마지막 열에도 `이력 시작 전·미확인`으로 표시한다. 저장소가 과거 시간표를 알고 있는 것처럼 위장하지 않는다.

## 설치 및 운영 절차

1. 반드시 **테스트용 Apps Script 프로젝트와 테스트용 시트**에서 먼저 확인하고, 기존 학교 데이터는 별도 백업한다.
2. `.claspignore`에 `RosterHistory.gs`와 `AdminAuth.gs`가 포함되어 있는지 확인한다.
3. 테스트 프로젝트에 변경된 파일을 올리고, 편집기에서 `setup_`을 실행한다. 이 과정에서 `RosterHistory` 탭과 기준선이 생성된다.
4. 기준선 시각 이전 날짜의 보고서가 미확인으로 표시되는지 확인한다.
5. 테스트 부원의 요일만 바꿔 새 이벤트의 `patch`가 `{"day":...}`인지 확인한다. 뒤이어 시간대를 바꿔도 이전 날짜의 당번은 변하면 안 된다.
6. 같은 날 점심 전·점심 후 사이에 배정 변경을 하면 각 시간대의 보고서가 각기 다른 시점의 배정 정보를 보여야 한다.
7. 테스트용 CSV에서 이전 학년·배정과 이력 확인 상태를 확인한다.

`setup_`은 한 번 실행한 후 재실행해도 이미 봉인된 기준선을 덮어쓰지 않는다. 사용자가 직접 스크립트 속성의 `ROSTER_BASELINE_AT`을 지우거나 이력 탭을 수정하지 않아야 한다.

## 정합성의 경계

Google Sheets는 다중 시트 쓰기에 대한 트랜잭션을 제공하지 않는다. `User` 행 갱신과 이력 이벤트 추가 사이에 일시적인 오류가 발생하면 불일치가 생길 수 있다. 이 경우 임의로 과거 이벤트를 새로 만들지 말고, 오류 시간과 현재 자료를 확인해 수동 복구해야 한다.

동일 스크립트에서 발생하는 일반적인 동시 변경은 `LockService.getScriptLock()`으로 직렬화한다. <https://developers.google.com/apps-script/reference/lock/lock-service>

## 이력 정합성 감사

`RosterAudit.gs`의 `api_rosterAudit`는 관리자 토큰을 요구하는 **읽기 전용** 검사다. 부원 관리 화면에서 **이력 점검**을 눌러 실행할 수 있다.

검사는 등록된 부원별로 이벤트를 재생한 마지막 상태를 현재 `User`와 비교하고, 기록 누락·잘못된 JSON·존재하지 않는 부원 참조·기준선보다 이른 이벤트·미래 이벤트를 보고한다. 정상이라면 부원 수와 이벤트 수를 표시한다.

불일치를 발견하면 일반적인 부원 수정·진급 작업을 중단한다. 데이터가 서로 다른 두 시트에 기록되므로 쓰기 도중 오류가 난 경우를 감지하려는 장치다. **자동 복구하지 않는다.** 담당자가 먼저 시트를 백업하고 원본 로그를 대조해 어떤 변경이 실제로 확정됐는지 검토해야 한다. 이 과정에서 이력 이벤트를 임의로 삭제하거나 다시 날짜를 매기는 것은 금지한다.

`RosterHistory` 이벤트는 부원당 매번 한 줄만 추가하며, 매일 빈 이력 행을 생성하지 않는다. 데이터량은 최초 등록 부원 수와 실제 변경 횟수에 비례한다.

## 쓰기 실패 대응과 복구 정책

`rosterSaveEventOrRollback_`은 신규 등록·수정·졸업·복귀·명단 제외 시 시간표 변경 이벤트의 쓰기에 실패하면, 이전 `User` 행으로 되돌리기를 시도한다. 신규 등록에서는 방금 만든 행을 삭제한다. 연간 진급은 `rosterPromoteOrRollback_`이 기존 부원 배열을 복구하도록 한다.

실패 경우를 구분한다.

1. **이력 저장 실패, 최신 상태 복원 성공:** 수정 요청을 실패로 반환하고 관리자가 이력 점검을 실행한다.
2. **이력 저장 실패, 복원도 실패:** 시스템이 작업 성공을 주장하지 않고 명확한 관리자 점검 오류를 반환한다.
3. **기록 일부는 성공했으나 서버에서는 실패로 관측:** 되돌리기만으로 문제를 해결했다고 단정하지 않는다. 뒤이어 이력 점검에서 최신 상태와 기록을 비교해야 한다.

Google Sheets는 두 탭 사이 원자적 커밋을 제공하지 않으므로 위 조치는 **최선의 노력에 의한 보상 작업(compensating action)**이다. 실제 트랜잭션 또는 자동 복구를 보장하지 않는다.

### 복구 시 지켜야 할 절차

- 담당자가 원본 시트를 백업하고 오류를 발생시킨 변경 시각 및 부원 ID를 확인한다.
- `User`의 현재 상태와 `RosterHistory`의 기준 상태 및 마지막 이벤트를 대조한다.
- 오류가 확인될 때까지 부원 편집과 연간 진급을 중지한다. 학생 출석 기록은 임의로 지우지 않는다.
- 부원 변경이 실제로 확정되었는지 판단하기 전에는 새 과거 이벤트를 생성하지 않는다.
- 잘못된 데이터를 정정해야 한다면 운영 책임자의 승인과 보존된 원본을 바탕으로 별도 복구 계획을 작성한다.

이 설계는 데이터 손상 감지와 통제된 복구를 우선한다. 무인 자동 복구는 의도적으로 구현하지 않았다.
