# 개발 브랜치 관리자 인증 안내

이 문서는 **개발용 Apps Script 복사본**을 대상으로 한다. 학교에서 사용 중인 웹앱은 그대로 둔다.

## 변경된 보안 경계

- 학생 출석(`api_attend`)과 보충 접수(`api_makeup`)는 종전처럼 공개되며, 관리자 승인 절차는 아직 없다.
- 출석 관리·CSV·부원 수정·삭제·졸업·복귀 API는 서버에서 관리자 토큰을 확인한다.
- `setup_`, `findSchool_`, `recordAbsencesToday_`, `promoteYearly_`는 Apps Script의 private 함수로 변경됐다. 브라우저의 `google.script.run`에서 직접 호출할 수 없도록 한 것이다.
- 로그인 시 관리자 비밀번호 자체는 저장하지 않으며, 인증 성공 시 브라우저 메모리에서만 관리 토큰을 유지한다. 캐시 세션은 최대 4시간이고 중간에 사라질 수도 있다.
- `CacheService`의 실패 횟수는 모든 방문자에게 공유된다. 다수의 실패 로그인으로 일시적인 관리자 로그인 차단이 발생할 수 있다. 이 방식은 대규모 외부 공개 서비스의 완전한 인증·속도 제한 체계를 대신하지 않는다.

## 개발 환경에만 설정

1. 원본 Apps Script와 **다른 Script 프로젝트 및 다른 Google Sheet**를 사용한다.
2. `node scripts/create-admin-credential.mjs`를 로컬 PC에서 실행한다.
3. 터미널에 표시된 관리자 비밀번호를 안전한 곳에 별도로 보관한다.
4. 함께 출력된 `salt:sha256` 값만 Apps Script의 **프로젝트 설정 → 스크립트 속성 → `ADMIN_PASSWORD_HASH`**에 저장한다.
5. `NEIS_KEY`, `SHEET_ID` 등도 개발용으로 분리하며 GitHub에 커밋하지 않는다.
6. `clasp push` 전 `.clasp.json`이 **운영 프로젝트가 아닌 테스트 프로젝트**를 가리키는지 반드시 확인한다.
7. Apps Script 편집기에서 `setup_`와 `findSchool_`을 차례로 실행한다. `setup_`은 기존 이름의 결석 트리거도 제거한 뒤 새 트리거를 등록한다.
8. 개발 배포 URL에서 미로그인 관리 페이지 접근 거부, 로그인 성공/실패, 세션 만료, 로그아웃, 학생 출석을 확인한다.

`ADMIN_PASSWORD_HASH`를 설정하지 않았다면 관리자 기능은 로그인되지 않도록 설계되어 있다. 저장소에는 비밀번호와 해시를 모두 올리지 않는다.

## 검증

Node.js 20 이상에서 별도 npm 설치 없이 다음을 실행한다.

```powershell
node --test tests/*.test.cjs
```

이 테스트는 가상 데이터와 서비스 모의 객체를 사용한다. Google Apps Script 배포/권한 및 실제 Google Sheet의 작동까지 보장하지 않는다.

## 운영 승격 전 확인

- 학교 출석 데이터를 별도 백업한다.
- 기존 운영 웹앱 버전과 개발 배포 버전을 비교한다.
- 교내 접근 정책에 맞는 실제 인증 방식인지 책임자와 검토한다.
- 보충 승인과 이력 조회 문제가 해결되지 않았다는 점을 담당자에게 알린다.
- 안준표 저장소의 `main`에는 충분한 검증과 승인 없이 직접 반영하지 않는다.

## 관리자 학년도 진급 절차

3월 1일 이후 새 학년도 진급은 **자동 처리하지 않는다.** 관리자 화면에서 `학년도 진급`을 열면 현재 재학생 중 3월 1일 이전에 등록된 부원의 변경 계획을 보여준다.

1. 신입생이 명단에 없는지 확인한다. 3월 1일 이후 등록된 신입생은 진급 대상에서 제외된다.
2. 기존 1·2학년이 각각 2·3학년으로 올라가는지 확인한다.
3. 기존 3학년은 졸업생으로 이동하며, 그동안의 출석 이력은 유지된다.
4. 관리자 담당자는 미리보기 명단이 올바른지 확인하고 확인란을 누른 뒤 `진급 확정`을 누른다.
5. 확정 시 서버가 대상 ID와 학년을 다시 계산해, 미리보기 이후 명단이 달라졌다면 적용을 거부한다.
6. 완료된 학년도는 `PROMOTED_YEAR` 속성으로 중복 실행을 막는다.
7. 실행 도중 오류가 발생하여 `PROMOTION_PENDING_YEAR`가 남으면 자동 재시도를 차단한다. 관리자는 이력 점검과 원본 시트 비교로 진급의 실제 완료 여부를 확인해야 한다.

신입생 추가, 조기졸업, 재학생 복귀, 시간표 수정은 부원별로 수행한다. 이 작업들은 저장 전에 이름·학년·요일·시간대를 다시 확인하는 화면을 보여준다.

**주의:** 기존 데이터의 `PROMOTED_YEAR`가 올바르지 않은 경우 값만 수동으로 조작해 중복 진급시키지 않는다. 학년도 전환 결과와 이벤트 이력을 대조한 뒤 운영 책임자가 판단해야 한다. 관리자 확정은 학교 운영본이 아니라 테스트 프로젝트에서 먼저 검증해야 한다.

## 학생별 예외가 있는 학년도 명단 정리

관리자 화면의 **학년도 정리**에서는 기존 재학생에게 기본 처리(1·2학년 진급, 3학년 졸업)를 제안한다. 각 학생 옆의 선택 메뉴에서 **진급 / 졸업 / 명단 제외 / 현 상태 유지**로 바꿀 수 있다. 3학년에는 4학년 진급 선택을 제공하지 않는다.

- **조기졸업:** 해당 학생의 처리를 `졸업`으로 선택한다.
- **재학 유지 또는 진급 유예:** `현 상태 유지`를 선택한다. 올해 정리 이후에도 별도 부원 수정은 가능하다.
- **도서부 명단 제외:** `명단 제외`로 변경한다. 학생 행과 출석·시간표 기록은 삭제하지 않으며, 관리자 명단의 제외된 부원 목록에서 복귀할 수 있다.
- **기존 졸업생:** 이번 학년도 처리 대상이 아니므로, 관리자 화면의 `졸업생` 목록에서 관리한다.
- **새 신입생:** `부원 추가`에서 등록한다. 3월 1일 이후에 추가된 학생은 올해 일괄 정리에서 제외한다.

학생별 처리를 바꾸면 확인란이 자동으로 해제되어 다시 검토해야 한다. 서버에서는 로그인, 기존 학년과 대상 명단, 처리 항목 및 중복 여부를 다시 검사한 뒤 적용한다. 처리 도중 결과가 불확실하면 기존과 같이 자동 재시도를 차단한다.

명단 정리는 **해당 학년도에 한 번만 확정할 수 있다.** 확정 후 잘못된 학생은 부원 관리에서 개별 조치해야 하며, 원본 이력을 덮어써서 일괄 정리를 재실행하지 않는다.

## 달력·시험·휴업일 기능 설치 확인

이번 변경은 기존 `User`와 `RosterHistory`를 그대로 사용하고, 새 시트 **`SchoolDays`** 및 **`AttendanceCorrections`**를 추가한다. 시험과 휴업일 설정은 `SchoolDays`에 변경분을 추가하는 방식이다.

개발용 복사본에서 먼저 `setup_`을 다시 실행해 새 시트 헤더가 생성됐는지 확인한다. 기존 저장소의 실제 Google Sheets를 백업하지 않고 스크립트를 운영 배포하지 않는다.

관리자는 **부원 관리 → 주간 당번 시간표 → 시험·휴업일 설정** 또는 **달력 → 등교·시험 일정**으로 들어갈 수 있다. 시험일은 첫날과 마지막 날을 지정하고, 첫날 **14일 전부터 마지막 날까지** 면제된다. 이미 결석 기록이 있다면 **출석 관리 → 해당 날짜 → 면제 정정**에서 개별 검토 후 처리한다.

기존 기록을 무조건 삭제하거나 과거 6개월의 시간표를 새롭게 추측하지 않는다. 재량휴업·방학·시험일은 관리자가 추가·수정·해제할 수 있으며 변경 이력이 시트에 남는다.

학생은 좌우 화살표로 오늘 다른 시간대 당번을 열람할 수 있으나, 출석은 **실제 서버가 판정한 현재 시간대**에만 허용한다.
